# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A plain PHP site (no framework, no Composer, no npm/build step — vanilla PHP + vanilla JS/CSS) with one front controller and a hand-rolled router. Four modules live side by side: `main` (home/contact/exchange-rates/ktane pages), `swat4`, `ss2`, and `music` (by far the largest and most actively developed — a song/artist/album cataloguing and rating tool, 60+ files).

## Commands

- **Run the test suite:** `php tests/run.php`. It copies the whole repo into a scratch temp dir (skipping `.sqlite`/`.db` files and a few static-asset dirs), boots PHP's built-in server against that copy, and drives it over real HTTP (via curl) through `tests/cases/*.php`. There is no per-test-name filter — every case file's tests run every time. Test case files are plain PHP files returning `['test name' => function ($ctx) { ... }]`; add new cases as new entries or new files under `tests/cases/`.
- **Check locale completeness:** `php tests/i18n-coverage.php` — lists untranslated/orphaned keys per music-module locale file; exits non-zero only on orphan keys (a locale file defining a key `en.php` doesn't have).
- **Rebuild the deploy folder:** `php build-deploy.php` — regenerates `_deploy/` (`_deploy/lotsofs.com/` = `public/`, `_deploy/app/` = `app/`) with dev-only files excluded and a set of sanity checks (required files present, `notes.txt`/`data`/`tests`/db files absent). `_deploy/` itself never ships and there's no CI — deploying means dragging `_deploy/`'s contents onto the host by hand.
- **Run a dev server directly:** `php -S localhost:PORT -t public` from the repo root. Because `app/modules/music/db.php` detects PHP's built-in server (`cli-server` SAPI) and switches to `music_test.sqlite` instead of `music.sqlite`, this is safe to use against the real repo without touching production-shaped data — and if `data/music.sqlite` exists and `music_test.sqlite` doesn't yet, it's seeded from a copy of it before migrations run.

## Architecture

### Request flow

`public/index.php` → `app/util.php` (constants + i18n) → `app/classes/Database.php` → `app/router.php`, which `include`s every module's `routes.php` into one `$routes` array (exact-path-string keys, no pattern matching) and dispatches by requiring the matching file. Unknown paths and non-canonical URLs (non-lowercase, trailing slash) get redirected/aborted in `router.php` itself.

### Module shape (repeats across `main`/`swat4`/`ss2`/`music`)

- `app/modules/<name>/routes.php` — the route table for that module, merged into the global one.
- `app/modules/<name>/routes/*.php` — page controllers: guard → load data via inline SQL → `require` a matching view. No model/service layer anywhere in this codebase — SQL lives directly in route and ajax files.
- `app/modules/<name>/views/*.view.php` — plain PHP templates.
- `app/modules/<name>/ajax/*.php` (music only, currently) — JSON POST endpoints for the front-end JS, gated by a shared `ajaxGuard.php` (JSON header, exception→500-JSON handler, POST-only, JSON-body parsing).
- `public/modules/<name>/{css,js,...}` — that module's static assets, served directly.

### The music module

This is where nearly all real work happens. Specifics worth knowing before touching it:

- **Storage:** SQLite via `app/classes/Database.php` (a thin PDO wrapper). `app/modules/music/db.php` picks `music.sqlite` or `music_test.sqlite` (see Commands above) under `__DATA__` (`/home/lotsofs/data` on the production host, `<repo>/data` everywhere else — this fallback is what makes local dev/tests work unmodified).
- **Migrations:** `app/modules/music/database/migrations/NNN_description.sql`, applied by `runMusicMigrations($db)` — called at the top of *every* music route and ajax file, so schema changes take effect on the very next request, tracked in a `schema_migrations` table **by filename only, with no content hash**. **Convention: once a migration has shipped to production, it is frozen — never edit it again, even for a typo. Any further schema change is a new, higher-numbered migration file.** Editing an already-shipped migration is a *silent* no-op against any database that already recorded it as applied — nothing errors, the schema just quietly stops matching the code, which surfaces later as a 500 on whatever query references the "added" column. `001`–`006` have shipped and are frozen; `007` is the next free number. The boundary moves every time something ships, so confirm it against `schema_migrations` rather than trusting this line. SQLite can't `DROP COLUMN` a column that's part of a `FOREIGN KEY`, so migrations touching such a column need a full create-copy-drop-rename table rebuild, not a plain `ALTER TABLE` (see `002_song_multi_artist_and_variants.sql` for a worked example, including why naively rebuilding a table that other tables hold live FKs into requires deferring FK checks and temporarily emptying/restoring those dependent tables around the rebuild — this failed silently at `COMMIT` in several simpler attempts before that approach).
- **The alias pattern:** `artist`/`song`/`album` each pair with an `..._alias` table (`artist_alias`, `song_alias`, `album_alias`) holding every name/spelling that entity has ever been called, with an `is_actual` flag marking the current one (enforced as *at most one* by a partial unique index — not *at least* one). This is how renames keep history and how "known misspellings" resolve to the right entity. Expect to see `LEFT JOIN ..._alias x ON x.<entity>_id = e.id AND x.is_actual = 1` throughout.
- **Songs can have multiple artists and albums:** `song_artist` and `album_track` are many-to-many join tables (no more single `song.artist_id`). The songs page shows every artist/album comma-joined; sorting/filtering still key off just the first linked artist.
- **`song_link`** is one row per song with a fixed column per platform (`spotify_url`, `youtube_url`, `soundcloud_url`, `bandcamp_url`, `filepath`, `other_url`), not a free-form link-per-row table — adding a new platform means a new column (migration) plus one entry in the `linkFields` config array that `routes/songs.php`/`songs.view.php`/`songs.js` all key off of, not a schema redesign. Spotify/YouTube accept either a full URL or a bare track/video ID (the ID is extracted and *that's* what gets stored, not the pasted URL — "precious bytes"); Spotify/YouTube/SoundCloud render as embedded players, the rest as plain links. Bandcamp is deliberately link-only, not embedded: its real embed needs a numeric ID that isn't in a normal page URL, and Bandcamp's oEmbed API returned a bot-detection challenge page when called server-side from this environment.
- **Card/table dual-DOM sync:** `/music/songs` renders the same song list twice — a `<table>` and a `<div id="songCards">` of `<dl>`s — kept in sync via `rowsBySongId` pairing each song's `<tr>` and card by id; `syncField()` writes a value to both trees at once. The modal (`#songCardModal`) *moves* a card's real DOM node in and out rather than cloning it. Admin-only "Edit" mode (`enterCardEditMode`/`exitCardEditMode` in `songs.js`) swaps specific fields (artist, album, year, links) for live editors backed by their own `/music/ajax/song-*` endpoints; it does not sync those edits back into the table row live (a reload picks them up) — only score/note (per-rater, not admin-gated) use the full `syncField` two-tree sync. **That pairing is positional** — `rowsBySongId` zips `songListBody.children[i]` to `songCardList.children[i]` — so nothing may ever be added as a child of `#songCards` or `<tbody>`; one stray element silently misaligns every song's row against the wrong card. This is why the toast container `#songToasts` sits outside `.songLayout` entirely.
- **Both cards share one set of chrome classes.** `.card`, `.cardIdRow`, `.cardIdCell`, `.cardEditBtn`, `.cardTitle`, `.cardModal`, `.cardModalDialog`, `.cardModalActions` and `.cardModalBtn` are styled once, near the top of the card CSS, and carried by the song card *and* the album card alongside their own names (`class="songCard card"`, `class="albumCardEditBtn cardEditBtn"`, …). Anything that should look the same on both belongs there; only what is genuinely particular — the song card's list sizing and field layout, the album card's tables — stays in the `#songCards, #songCardModal` and `.albumCard` blocks. The song-specific names are still in the markup because `songs.js` and the tests select on them, so add to a class list, never replace one. A test that splits HTML on a card's opening tag must match the class attribute loosely (`songsCardFor` uses a regex for exactly this reason).
- **Cards are partials, not view code.** A song card is `views/partials/songCard.php`, rendered per row out of `views/partials/songRows.php` — the one pass that derives every escaped value/class/attribute both the table and the card need (require it first, over `$globalData['songs']`; everything songs-page-specific in it falls back to null/empty so another page only has to supply `songs` and `raters`). An album card is `views/partials/albumCard.php`, rendered server-side by `/music/ajax/album-card` into `{html}` and dropped into `#albumCardModal` by `albumCard.js`, which is wired on both `/music/songs` and `/music/albums` by one delegated listener over `data-album-card-id`. That attribute is the whole contract: put it on anything clickable (the song table's album cell, the song card's, the album list's name) and the card opens; `songs.js` re-adds it when its album editor leaves edit mode. Its Escape handler is **capture-phase and stops the event**, because the song modal's own Escape handler would otherwise close that one out from under it. Unlike the song card, the album card's admin edit mode does **not** patch the DOM on the way out — "Done" just re-fetches the card, which is what makes track titles, the artist name and the per-rater statistics agree with what was just written; the card response carries only `trackAliases` (the names of the songs already on this album, admins only) — the artist and song dropdown lists are the **whole catalogue**, so `/music/ajax/album-options` fetches them on the first Edit click of a page session and `albumCard.js` keeps them from then on. Do not fold them back into the card: measured at 10k songs they are 24.6ms and 636KB *per card open*, against 0.42ms for everything else the card does, and most opens never edit anything. A song added mid-edit gets its alias list back from its own `album-track` `add` response for the same reason.
- **Every blue on a music page is one CSS custom property, `--hue`.** `styles.css` defines it on `:root` as 240 (the original site blue) and expresses every blue-ish colour as `hsl(var(--hue), …)`; `partials/head.php` stamps the signed-in account's hue onto `<html>` as an inline style, which overrides it for that user only. Keep the `:root` value — without it every one of those declarations resolves to nothing, not to blue. The hue also colours that rater's dots on an album card graph, so it is a person's colour everywhere, not just their own chrome. An account that has never picked one gets `(id * 73) % 360` from `musicHueFor()` in `hue.php`, and `account.hue` stays NULL until they choose — so "the default" is derived, never stored, and new accounts land on distinct colours without registration writing anything.
- **The album card's per-track graph is hand-written inline SVG** in `albumCard.php` — no charting library, because there is no build step and the card renders server-side for two different pages. One dot per score, every rater's dot for a track on that track's single x so a column reads down as "what everyone thought of this one" (an earlier version nudged each rater sideways to keep ties visible; that was dropped for column alignment, so identical scores now overlap deliberately), and dots joined only across tracks the same rater scored — a line across a gap would draw a score nobody gave. Rater colours are keyed to account id in a fixed order, *not* to the row order of the stats table — that table puts the current viewer first, and a graph that recoloured itself per viewer would make two people describing the same album talk past each other. The swatch in the stats table is the legend, so the graph needs none.
- **Average/median/mode/σ are worked out in PHP, not SQL.** SQLite has no `stddev()` and median/mode are painful in SQL, so `ajax/albumCard.php` pulls one `ORDER BY score` list per account and does all four in one pass (the sort is what lets the median be read off the middle). They are over *the tracks that rater scored*, never over the album, which is why every row also prints `rated / total` — and why all-distinct scores print no mode at all rather than listing every score as one.
- **Live rating updates use one poll with two cursors that behave oppositely — do not "harmonise" them.** `/music/ajax/song-rating-poll` takes `since` *and* `sinceAudit` in one request. `since` filters `account_song.updated_at` with an **inclusive** `>=`, so it deliberately re-delivers the same row every tick (a test pins this: a second write inside the same one-second stamp must not slip through); that's harmless because the client just rewrites cells to the same values. `sinceAudit` filters `rating_audit.id` with a **strict** `>`, because those rows drive one-shot popup notifications and an inclusive cursor would re-fire the same popup every 3 seconds forever. Making either match the other breaks one of the two features, silently.
- **`rating_audit`** (migration `005`) is an append-only log of score/note writes — one row per change with `value`, `previous_value` and the account, written by `ajax/songRating.php` inside a transaction with the `account_song` upsert. The transaction matters: a state change without its audit row is invisible forever, since the audit cursor only ever moves forward. Identical rewrites are deliberately not logged. `account_song` still holds only current state; this table is the only history.
- **Sticky table header: its borders are `box-shadow`, not `border`.** With `border-collapse: collapse` the *table* paints collapsed borders, so they stay behind at the table's original position when `thead` sticks — real borders on header cells look correct at rest and vanish the moment the header locks (rows then show through the 1px seams). Every header edge is therefore an `inset` shadow, drawn right-edge-per-cell so shared separators stay 1px. Related trap: `.songListScroll` must **not** regain `overflow-x`, because one axis of `auto` makes `overflow-y` compute to `auto` too, turning it into a scroll container — the header would then stick to *that* box (which never scrolls vertically) instead of the viewport. The cost of removing it is that an over-wide table scrolls the page sideways.
- **`--songNavHeight` is measured in JS**, published onto `<html>` by a `ResizeObserver` in `songs.js` and consumed by CSS `calc()` for the sticky header's top and the toast stack. The nav wraps, so hardcoding it reopens the bug where body rows show through the gap between the nav and the locked header. Measure with `getBoundingClientRect().height`, not `offsetHeight` — the latter rounds to whole pixels, which is what made a 1px fudge necessary before. (There was a `--songHeaderHeight` beside it, read only by the note preview panel's sticky offset; both went when that panel was deleted.)
- **Auth/session:** `app/session.php` provides `sessionScope()`-namespaced sessions (so future non-music modules can have entirely separate accounts), CSRF via `csrfToken()`/`checkCsrf()`, and `requireLogin()`/`requireLoginJson()` guards. `app/modules/music/auth.php` layers admin-only checks on top.
- **i18n:** `loadStringCatalogue($module)` selects a module's strings; `stringCatalogue()` reads them back and `t($key, $params)` translates. Each module has `lang/en.php` (the source catalogue, always complete) plus `lang/<locale>.php` overlays; missing/blank overlay keys fall back to English automatically. Active locale comes from the session, else the `LOTSOFS_LOCALE` env var, else the module's own `defaultLocale` in `app/modules/<name>/config.php` — `fy` (West Frisian) for music, the site default for real visitors. The test harness sets `LOTSOFS_LOCALE=en` so assertions can match English text. `tests/cases/strings.php` fails the suite if a catalogue key is referenced nowhere (`t('literal.key')` must appear verbatim somewhere under `app/modules/music` or `public/modules/music` — dynamic/glued key lookups don't count) or if a key exists in one locale but not another.
- **Bulk import** (`/music/add-songs`): paste tab-separated rows, then a column-mapping step lets you assign each column a role (Artist/Title/Album/Track#/Year/one of the link platforms/Ignore) rather than assuming a fixed column order — content is auto-guessed where it's unambiguous (a Spotify/YouTube/SoundCloud/Bandcamp URL or a bare Spotify/YouTube ID), position-based only for the first four columns. Wizard order is Artist → Song (titles/aliases only) → Extras (links + year, confirm-and-submit, generalized for future per-song data) → Album (its year input pre-filled from whatever the Extras step just confirmed) — Extras deliberately runs *before* Album so the year is available to pre-fill it.

## Environment gotchas

- **No `mbstring`.** No `mb_*` function works on this PHP build (and presumably not on the host either) — use `strlen` and friends.
- **`proc_open` on Windows spawns through a shell wrapper**, so `proc_terminate` only kills the wrapper and orphans the real child process. `bypass_shell => true` (already used in `tests/run.php`) is required to avoid leaking a server process per test run.
