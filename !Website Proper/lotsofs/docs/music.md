# The music module

Imported by `CLAUDE.md`. The largest module by far, and where nearly all real work happens.

### Storage and migrations

- **Storage:** SQLite via `app/classes/Database.php` (a thin PDO wrapper). `app/modules/music/db.php` picks `music.sqlite` or `music_test.sqlite` (see Commands above) under `__DATA__` (`/home/lotsofs/data` on the production host, `<repo>/data` everywhere else — this fallback is what makes local dev/tests work unmodified).
- **Migrations:** `app/modules/music/database/migrations/NNN_description.sql`, applied by `runMusicMigrations($db)` — called at the top of *every* music route and ajax file, so schema changes take effect on the very next request, tracked in a `schema_migrations` table **by filename only, with no content hash**. **Convention: once a migration has shipped to production, it is frozen — never edit it again, even for a typo. A deploy ships at most one new migration (the owner's rule, 2026-11-05): every schema change until the next deploy goes into the one unshipped file, whose header lists each change, and a new, higher-numbered file is started only once that one has shipped.** Editing an already-shipped migration is a *silent* no-op against any database that already recorded it as applied — nothing errors, the schema just quietly stops matching the code, which surfaces later as a 500 on whatever query references the "added" column. `001`–`009` have shipped and are frozen (`009` deployed 2026-11-05). No file is unshipped: the next schema change starts `010`, which can be edited or renamed until it ships. An edit to the unshipped file is a silent no-op on a database that has already run it, `music_test.sqlite` included, so delete that file afterwards: the next dev-server request copies `music.sqlite` again and runs it. The boundary moves every time something ships, so confirm it against `schema_migrations` rather than trusting this line. SQLite can't `DROP COLUMN` a column that's part of a `FOREIGN KEY`, so migrations touching such a column need a full create-copy-drop-rename table rebuild, not a plain `ALTER TABLE` (see `002_song_multi_artist_and_variants.sql` for a worked example, including why naively rebuilding a table that other tables hold live FKs into requires deferring FK checks and temporarily emptying/restoring those dependent tables around the rebuild — this failed silently at `COMMIT` in several simpler attempts before that approach).

### The data model

- **The alias pattern:** `artist`/`song`/`album` each pair with an `..._alias` table (`artist_alias`, `song_alias`, `album_alias`) holding every name/spelling that entity has ever been called, with an `is_actual` flag marking the current one (enforced as *at most one* by a partial unique index — not *at least* one). This is how renames keep history and how "known misspellings" resolve to the right entity. Expect to see `LEFT JOIN ..._alias x ON x.<entity>_id = e.id AND x.is_actual = 1` throughout.
  **A name can be written in, deleted, or made current again, from the card's edit mode**, through one row per other name drawn by `public/modules/music/js/aliasEditor.js` on all three cards, with a + under them that opens a box for another, as the song card's artist and album rows wait behind theirs (the owner's choice: an empty box on every card in edit mode was clutter). The box saves on blur, as every other box in the card editors does, and Enter does the same and opens a fresh box with the cursor in it; a save redraws the rows, so the + is back otherwise. It posts `/music/ajax/alias-add`, which trims the name, answers `duplicate` for a name the thing already has, stores it as not current unless the thing has no names at all, and refuses a song a name another song by any of its artists goes by, as a rename does: an import of that name could no longer tell the two apart. Edit mode makes the row when the card has none, which on the song card means a song with one name gets it too. Typing a name and going straight to Done saves after leaving edit mode has taken the empty row away, so `aliasFieldEditor` puts the row back for that case. "Use this name" is no endpoint of its own: it is a rename to that name, and `song-edit`, `album-edit` and `artist-edit` all promote a name the thing already has. Each rename endpoint returns the names as they now stand (`titles` for a song, `names` for the others), current first, from `musicAliasNames()` in `aliases.php`, and the rows redraw from that. Deleting is `/music/ajax/alias-delete`. It refuses the current name, which is the `is_actual DESC, id` first row the cards show, and that also keeps a thing from losing its last name. Every delete asks first (`confirm()`), because a song name cannot be added back from any card. **A song name an album lists the track under is held back**, because `album_track.song_alias_id` holds an enforced foreign key into `song_alias`. The answer is `status: listed` with the albums, and the row offers a button that sends `clear_listings: true`, which sets those tracks back to NULL (their current title) and deletes the name in one transaction. The owner asked for the refusal and the way past it together, so nobody has to hunt the albums down. The song list's client copy of those listings (`songTrackAliases`) drops the name too, or switching to that album would bring it back.
- **Songs can have multiple artists and albums:** `song_artist` and `album_track` are many-to-many join tables (no more single `song.artist_id`). The songs page shows every artist/album comma-joined; sorting/filtering still key off just the first linked artist.
- **Two songs can be related, one row per pair** (`song_relationship`, its type column since migration `009`). The variant is the derivative and the target the original, and the type names the row from either end: `remaster` reads "remastered version of …" on the variant's card and "original version of …" on the target's, so the two directions cannot disagree and there is no second row to keep in step. **The types are a list in code**, `musicSongRelationTypes()` in `relationships.php`, with their names in the catalogue (`relation.*`), not a table: the owner wanted them translated like every other label. Only `remaster` exists; another kind is one entry there plus its two labels in each locale. A kind gets id columns in the song table only through its `columns` entry, keyed by the end whose row each is on, with those keys also in `MUSIC_SONG_COLUMNS` and in the stylesheet's left-edge chain and hide list. A code no longer in the list still shows, as itself. `musicSongRelations()` is the one SELECT, for the song list and the endpoint alike, and `musicSongRelationExists()` is the only guard against a second row for the same pair and type, since the table has no index, and it checks both ways round: the reversed row would put contradictory lines on the two cards. The song card shows its rows under Related, after Also Known As, each line naming the other song by id and title ("original version of 5: *Title*", the title in italics), since two songs may share a title, and linking its card. The table has no such lines: it lists the other song's id under its kind's own column (Remastered by on the original's row, Remaster of on the remaster's) and the other song's names under Other names (see The song list page). **Edit mode works as artists and albums do**: every row, saved or new, is a kind select and a song, saved whenever both are set and either changes, so a saved row is changed in place (`update`, keeping its id) rather than deleted and re-added; a + adds a row, and × removes one. **The song is typed, not picked from a dropdown**, since a list of every song is unusable past a few hundred: one shared `<datalist>` of every song on the page, labelled `Artist — Title · Albums`, with ` #id` added to a label that would still repeat, because the label is the only thing that maps back to a song id. A picked suggestion saves at once; typing saves on Enter or leaving the box, since one label can begin another, and a name that matches no song puts a saved row's song back. Every answer from `/music/ajax/song-relationship` carries the lists of every song it changed, the one a moved row left included, and redraws their rows and cards. A line names the other song as it was called when the page loaded, so a rename shows there after a reload. The import writes one too (below), which is how a re-recording gets in at all: a song's title is otherwise unique per artist.
- **`song_link`** is one row per song with a fixed column per platform (`spotify_url`, `youtube_url`, `soundcloud_url`, `bandcamp_url`, `filepath`, `other_url`), not a free-form link-per-row table — adding a new platform means a new column (migration) plus one entry in the `linkFields` config array that `routes/songs.php`/`songs.view.php`/`songs.js` all key off of, not a schema redesign. Spotify/YouTube accept either a full URL or a bare track/video ID (the ID is extracted and *that's* what gets stored, not the pasted URL — "precious bytes"); Spotify/YouTube/SoundCloud render as embedded players, the rest as plain links. Bandcamp is deliberately link-only, not embedded: its real embed needs a numeric ID that isn't in a normal page URL, and Bandcamp's oEmbed API returned a bot-detection challenge page when called server-side from this environment.

### The song list page

- **Card/table dual-DOM sync:** `/music/songs` renders the same song list twice — a `<table>` and a `<div id="songCards">` of `<dl>`s — kept in sync via `rowsBySongId` pairing each song's `<tr>` and card by id; `syncField()` writes a value to both trees at once. The modal (`#songCardModal`) *moves* a card's real DOM node in and out rather than cloning it. Admin-only "Edit" mode (`enterCardEditMode`/`exitCardEditMode` in `songs.js`) swaps specific fields (artist, album, year, links) for live editors backed by their own `/music/ajax/song-*` endpoints; it does not sync those edits back into the table row live (a reload picks them up) — only score/note (per-rater, not admin-gated) use the full `syncField` two-tree sync. **That pairing is positional** — `rowsBySongId` zips `songListBody.children[i]` to `songCardList.children[i]` — so nothing may ever be added as a child of `#songCards` or `<tbody>`; one stray element silently misaligns every song's row against the wrong card. This is why the toast container `#songToasts` sits outside `.songLayout` entirely.
- **Hover tooltips: put `data-tooltip` on anything.** `views/partials/tooltip.php` (included by `foot.php`, so it is on every music page) ships one `#musicTooltip` box and `js/tooltip.js`, which listens **delegated** on the document rather than binding per element — most of what wants a tooltip here is fetched and injected after load, so anything bound at page load would miss it. **`data-tooltip-rich`** beside `data-tooltip` holds the same text as `[[piece, bold], …]` and is shown instead, built with `textContent` only, since a piece can be a title or a note somebody typed: that is how a rating cell's list of other versions has its sentences bold and the ratings plain. `musicTooltip.link(el, text)` exists for the imperative case, mirroring the `tooltipPopup.link()` in `public/modules/ss2/js/ui/tooltip.js` this was modelled on (deliberately a copy, not shared code: ss2's is an ES module and the two modules ship separate stylesheets). An element that also carries its own SVG `<title>` gets it removed on first hover, or the browser's native tooltip surfaces a second later underneath ours; the title is what makes the same text available with no JS, so emit both. The box is `white-space: pre-line`, so `\n` in the attribute is a line break — that is how the album graph's columns list a song title followed by one line per rater. Inside a container marked **`data-tooltip-titles`** a plain `title` attribute counts as a tooltip too, which is how the song table's clipped cells were upgraded without touching a cell: the server still emits `title`, so the value is reachable with no JS, and the attribute is *moved* into `data-tooltip` on first hover. That move is why `setCellValue()` and the album editor's `exit()` in `songs.js` write whichever of the two a cell currently has — writing only `title` would leave a hovered cell's tooltip stale while the cell itself was right.
- **The table has three columns for names and versions: Other names between Title and Album, and Remastered by and Remaster of between Links and the raters** (the owner split one Other names & versions column into these on 2026-11-06, a day after merging two into it). The card keeps its own two rows, Also Known As and Related, and lists only the song's own names. Other names starts hidden and the id columns shown. **Other names is the song's other names, then every name its versions go by that it does not**, exactly as written, once each however many versions share it. Each is a line (`.songAlias`) clipped at 14em with its whole text in its `title`. A version's name is italic and dotted-underlined (`.songVersionHint`), and its tooltip adds a line per version that goes by it ("Name of the remastered version (12)"). **The id columns list the other song of each relationship of their kind and end**, lowest id first, each a link opening its card. An id whose song is called otherwise than this song's current title is marked the same way, with "as *its title*" as its tooltip. Neither sorts. Their headers are short labels ("Rem." over "by"), since a full one held the column at about 128px for ids a few digits wide, with the full name (the type's `columns` `name`) in the header's `title` and the column picker, as the statistics' short labels have. The columns are 2.6em wide, a statistic's width, and only the body cells are `nowrap`: the width is what makes the label wrap, because a table narrower than the screen gives every column room for its label on one line. `songRows.php` writes all three, and `applyAliasCell()` and `applyRelationCells()` in `songs.js` redo them the same way from the page, so the two must change together. Since the table has no relations cell, the row's `<tr>` carries `data-relations`, which `songRelations()` reads for both and for `lendingVersions()`. A version's names and title are read off its own row (`songNames()`, `data-canonical-title`), so `refreshVersionCells()` redraws a song's row and every related song's row after a rename or a name added or deleted, and a relationship's answer redraws every row it names. **The other names are every name but the one the Title cell shows.** The names come from one query in `routes/songs.php` (`namesBySong`, current first, the rest by name), which also builds the title's tooltip, so the two cannot disagree. A track that an album lists under another name is retitled when the list is filtered to that album, so its real title moves into this column. The cell (`data-field="aliases"`) carries every name as JSON in `data-titles`, and `applyAliasCell()` in `songs.js` redoes it whenever `applySongTitles()` changes the title: as lines in a row, as plain text in the card. Only songs with a name besides their current title carry the attribute; `songNames()` falls back to the title for the rest. A rename refreshes it from the `titles` that `song-edit` now returns, along with `data-canonical-title`, which used to go stale and come back on the next album switch. The value is not a `.songCellText` of the Title cell, so sorting, toasts and the title editor never see it. The column does not sort: it has no `data-sort-key`, like Links. Every card has an Also Known As row when the song has another name, and a Related row when it has a relationship, whatever the picker says. The card's names are `pre-line`, so a long one wraps.
- **The column picker hides table columns with CSS only; every cell is still rendered.** That is not for speed: `songs.js` reads a row's title and artist whatever is on screen (toasts, sorting, the card sync), and a toggle has to take effect at once. Each pickable column has a class on `#songListTable`, `songHide` + its key (`songHideAliases`, `songHideAverage`), and `songHideRater<id>` for a rater. The fixed and statistic columns hide by static rules at the end of the `#songListTable` block. A rater's rule is written per rater into the `<style>` at the top of `songs.view.php`. It matches the body cells by `data-account-id`, the score and note headers by their `data-sort-key`, and the name header by a `songRaterGroup<id>` class. The header cells' attributes are pinned by the colour tests, so no new attribute could be added. The reader's own columns can be hidden too. **Choices are rows in `account_song_column`** (migration `009`): one per column the person has ticked or unticked, keyed as above with raters as `rater_<id>`. A column with no row takes its default from `songColumns.php`, where only `aliases` (Other names) starts hidden, so a column added later gets its own default even for someone who has already chosen. A change is posted to `/music/ajax/song-columns` as one upsert. `songs.js` queues those saves one at a time, so two quick clicks on the same box land in order. **Hiding the first column must not take the table's left edge with it.** The ID column draws that edge, Average draws the statistics block's, and a chain of rules hands each edge to the next column when every column before it in its block is hidden, in both the header (the four-sided shadow) and the body. The rules are static and need no JS, so a column added left of the raters needs its line in both chains, after every column before it. Raters draw their own edges and need no chain. The picker does nothing to the cards, and card view hides it. Deviation and Rated are dimmed on their contents (`td > *`), not the cell: on the cell, the opacity dimmed their lines too, which left them fainter in the body than in the header, and that showed once Deviation drew the block's edge.
- **The text columns can be dragged wider or narrower, in this browser only** (the owner's choice, 2026-11-05: a convenience, not an account setting). Artist, Title, Album, Other names and each rater's Note get a `.songColumnGrip` on their header's right edge from `songs.js`. Numbers, scores and statistics have none, since they cannot shrink below their digits. A width is a custom property on `<html>`, in em (`--songWidthArtist`, `--songWidthRater<id>`). The stylesheet reads it three times per column: as the cell's `width`, its `min-width` and its clip's `max-width`, each falling back to what the column had before. **The `min-width` is the one that holds**: the table is laid out at about its narrowest, where a cell's `width` counts for nothing. That is also why a note column renders well under its nominal 12em. A rater's note column reads its property through `--songNoteWidth`, set per rater in the view's `<style>` beside the picker's rule. An unset property leaves that mapping invalid, so the default applies. The widths live in `localStorage` as `musicSongColumnWidths`, keyed by property name. The inline script at the top of `songs.view.php` sets them before the table is parsed, so a reload never flashes the default widths. Double-clicking a grip gives the column its own width back.

### Cards

- **Both cards share one set of chrome classes.** `.card`, `.cardIdRow`, `.cardIdCell`, `.cardEditBtn`, `.cardTitle`, `.cardModal`, `.cardModalDialog`, `.cardModalActions` and `.cardModalBtn` are styled once, near the top of the card CSS, and carried by all three cards alongside their own names (`class="songCard card"`, `class="albumCardEditBtn cardEditBtn"`, …). Anything that should look the same on both belongs there; only what is genuinely particular — the song card's list sizing and field layout, the album card's tables — stays in the `#songCards, #songCardModal` and `.albumCard` blocks. The song-specific names are still in the markup because `songs.js` and the tests select on them, so add to a class list, never replace one. A test that splits HTML on a card's opening tag must match the class attribute loosely (`songsCardFor` uses a regex for exactly this reason).
- **There are three cards and one modal.** A song card is rendered into the page; an **album** card and an **artist** card are fetched (`/music/ajax/album-card`, `/music/ajax/artist-card`) into the *same* `#albumCardModal` — the id and `albumCard.js`'s name predate the artist card and now undersell both. Each fetched card carries `data-card-kind` and `data-card-id`, and everything after the fetch — the order control, the Edit button, the re-render — reads those rather than knowing which kind it has. Adding a fourth kind means an entry in `CARD_KINDS`, an endpoint, and a partial. The **ratings table** (`partials/scoreStats.php`), the **graph** (`partials/scoreGraph.php`) and the score formatting/colouring (`partials/scorePresentation.php`) are shared by album and artist: pass `$graphNaturalLabel = null` where there is no inherent order (an artist's songs are a set, so "Album order" disappears from their dropdown). An artist card deliberately has **no track list** — it would be every song they ever recorded — but does list their albums, each opening its own card, so the two walk to each other. Their CSS is one comma-separated block (`.albumCard, .artistCard`), which is the nested-group trap in `conventions.md`: resolve a selector by walking *up* to that line, not to the nearest brace.
- **Cards are partials, not view code.** A song card is `views/partials/songCard.php`, rendered per row out of `views/partials/songRows.php` — the one pass that derives every escaped value/class/attribute both the table and the card need (require it first, over `$globalData['songs']`; everything songs-page-specific in it falls back to null/empty so another page only has to supply `songs` and `raters`). An album card is `views/partials/albumCard.php`, rendered server-side by `/music/ajax/album-card` into `{html}` and dropped into `#albumCardModal` by `albumCard.js`, which is wired on `/music/songs`, `/music/albums` and `/music/artists` by one delegated listener over `data-album-card-id`. That attribute is the whole contract: put it on anything clickable (the song table's album cell, the song card's, the album list's name) and the card opens; `songs.js` re-adds it when its album editor leaves edit mode. Its Escape handler is **capture-phase and stops the event**, because the song modal's own Escape handler would otherwise close that one out from under it. Unlike the song card, the album card's admin edit mode does **not** patch the DOM on the way out — "Done" just re-fetches the card, which is what makes track titles, the artist name and the per-rater statistics agree with what was just written; the card response carries only `trackAliases` (the names of the songs already on this album, admins only) — the artist and song dropdown lists are the **whole catalogue**, so `/music/ajax/album-options` fetches them on the first Edit click of a page session and `albumCard.js` keeps them from then on. Do not fold them back into the card: measured at 10k songs they are 24.6ms and 636KB *per card open*, against 0.42ms for everything else the card does, and most opens never edit anything. A song added mid-edit gets its alias list back from its own `album-track` `add` response for the same reason.
- **Other people's ratings are covered until this reader has one of their own.** Two gates, and they are independent: with nothing in this reader's own **note** cell for a song, every other rater's note on it is covered; with nothing in their own **score** cell, every other rater's score is, and so are the seven value statistics, which are over everybody's scores. A note does not buy you the scores and a score does not buy you the notes. The `rated` count is never covered — how many people have an opinion gives away nothing about what it is — and neither is an empty value or one of your own. `0` is a real score, which is why both languages test `=== null` / `=== ''` and `.trim() === ""` rather than truthiness.
  The point is not secrecy, it is not reading someone else's verdict before forming your own, so **the value is still in the page**: `songRows.php` marks the cell and the view renders a pill in front of the value rather than withholding it. What *is* withheld is the `title`, whose tooltip would otherwise hand the note straight back on hover, and the `songScoreColoured` class, because `hsl(score * 12, …)` is the number back again. One pill, `.songGateReveal`, with the long label where there is room — the card, and the table's 12em note columns — and the short one in the table's 2em score and 2.6em statistics columns, which take the width of whatever is in them.
  `applySpoilerGate()` in `songs.js` keeps it right afterwards, called from the bottom of `setCellValue()` — the one place every value change passes through, so it covers this reader writing a rating, clearing it again, the poll bringing somebody else's in, and `applySongStats()` rewriting the statistics. Four things in it are load-bearing. `ownValue()` reads a live `input`/`textarea` rather than the cell text, because `beginCellEdit()` empties the value element and a poll tick mid-edit would otherwise read "nothing written" and drop the gate over the whole row while the reader is looking at it. `SONG_RAMP_FIELDS` is read off the header row rather than from a second list of statistic names, so putting the colour back after a reveal cannot drift from `routes/songs.php`. The revealed set is keyed by song **and `data-field`**, not by account, so one rater's score and note stay two separate reveals and the row and the card agree. And the tbody click listener returns early on a `.songGateReveal`: `tbody` is a nearer ancestor than `document`, so without that guard clicking a pill in a note cell would pop the card modal as well.
  **Toasts follow the same two gates**, read off this reader's own cell in the table row. A covered toast still names the person and the song and drops only the value, through four templates of its own — `fillFromTemplate()` emits an unmatched `{value}` *literally*, so the value is suppressed by switching template, never by dropping the part. A song the page never rendered has no cell to read and is covered, which is the safe direction.
  **The switch is `account.blind_rating`** (migration `007`), read through `musicBlindRating()` in `blindRating.php`, primed into the session at login beside the hue and forgotten at logout — module preferences live outside the session's scope key, so `logOut()` does not touch them. The cog menu in the nav is the only thing that writes it. Its route differs from its colour and language siblings in one way worth knowing: an unticked checkbox is simply absent from the body rather than present and invalid, so a valid post is authoritative for both values and "missing" means off.
  **Four leaks are deliberate**, decided rather than overlooked. `/music/audit` lists every change by everyone with both values, non-admin readable — opening it is a deliberate act. The album and artist cards are untouched, including the graph's per-track tooltips. The values stay in the page HTML and on the poll's wire, which a test pins on purpose so nobody "fixes" it server-side. And sorting still ranks covered values: `?sort=score_7` orders by a rater whose cells read as pills.
  One CSS trap: the hiding rules carry **three** id prefixes — `#songListTable`, `#songCards` *and* `#songCardModal`. The rules they have to beat (`.ratingNoteText`, `.songCellText`) sit inside those blocks and so resolve at id specificity; a bare `.songGated .songGateValue` loses to them and leaves the value on screen behind the pill. Two of the three gets a bug that only shows in one view.

- **Every blue on a music page is one CSS custom property, `--hue`.** `styles.css` defines it on `:root` as 240 (the original site blue) and expresses every blue-ish colour as `hsl(var(--hue), …)`; `partials/head.php` stamps the signed-in account's hue onto `<html>` as an inline style, which overrides it for that user only. Keep the `:root` value — without it every one of those declarations resolves to nothing, not to blue. The hue also colours that rater's dots on an album card graph and their name on a rating toast. The shades differ on purpose: the toast name is `hsl(hue, 100%, 60%)`, the nav swatch beside the colour picker, so it reads as the colour that person picked; the graph's dots are the softer `70%, 62%` of `scoreRaterColours()`. The poll sends the hue rather than a finished colour; `toastName()` in `songs.js` builds it. Nothing here corrects for a particular hue, so text in a hue stays readable by being light: at 60% a deep blue is 3.1:1 against black. **The song list draws nobody in their own colour.** For a day (2026-11-03) the names over the rater columns, a card's score and note labels and the edges of every rater's columns were in that rater's hue; the owner took all of it back out (a test pins it). What is left is the reader's own columns edged in the grey `--mineAccent`, as inset shadows in the header and the body alike (`thead .songMineGroup`, `.songMyScoreCell`, `.songMyNoteCell`). Their note column's right line is the accent alone, with the cell's border taken off, because that is how the header draws it, and a border and a shadow round differently at a fractional display scale, so the edge would shift between the two. The suite cannot see any of this. Check a change here by comparing a pixel row from the header with one from the body across every edge at more than one scale: one boundary can line up while its neighbours do not. An account that has never picked one gets `(id * 73) % 360` from `musicHueFor()` in `hue.php`, and `account.hue` stays NULL until they choose — so "the default" is derived, never stored, and new accounts land on distinct colours without registration writing anything.
- **The per-track graph is hand-written inline SVG** in `partials/scoreGraph.php` (shared by the album and artist cards; it was inline in `albumCard.php` until the artist card needed it) — no charting library, because there is no build step and the card renders server-side for several pages. One dot per score, every rater's dot for a track on that track's single x so a column reads down as "what everyone thought of this one" (an earlier version nudged each rater sideways to keep ties visible; that was dropped for column alignment, so identical scores now overlap deliberately), and dots joined only across tracks the same rater scored — a line across a gap would draw a score nobody gave. The x order is a dropdown (album order where there is one, release year where the songs carry one, title, any of the seven statistics, rated count, duration, or any one rater's scores, each with a direction that starts at the order's natural reading and can be flipped). Two of those are conditional: the natural order disappears when `$graphNaturalLabel` is null, and release year is offered — and leads the list, so it becomes the default — only when some song has a year, which is why an artist card opens chronologically and an album card does not. **Only the graph reorders** — the track table keeps the album's running order, which is the one thing about a record that isn't a statistic. The sort happens server-side and the card re-renders, which keeps the SVG geometry in one place instead of reimplementing the run-splitting in JS; `albumCard.js` holds the choice for the page session and passes it with every card request, and preserves the dialog's scroll position across the re-render. A sort key *or direction* the partial doesn't recognise falls back to the order's own default rather than being coerced — coercing an unknown direction to `desc` silently reverses the album. Rater colours are keyed to account id in a fixed order, *not* to the row order of the stats table — that table puts the current viewer first, and a graph that recoloured itself per viewer would make two people describing the same album talk past each other. The swatch in the stats table is the legend, so the graph needs none.

### Statistics

- **Every rating is read through `effective_rating`, which lends a song its versions' ratings.** A rater with no score on a song takes the average of their scores on its other versions, and with no note the note they wrote last among them, by `rating_audit`'s time (every note written since migration 005 is audited, so a note from before it is older than any audited one, and only between such notes does `account_song.updated_at` decide; it moves on score writes too, so it cannot say when a note was written). The versions are the songs a relationship of a kind with `inherits` in `musicSongRelationTypes()` ties it to, directly: `remaster` lends, and a chain does not pass ratings on (CHN). **A borrowed rating counts as the rater's own everywhere** — the song list's statistics, its Rated count and its sorting, both lists, both cards and the graph — and only a real rating replaces it; nothing is written for it, and `account_song` stays the only thing written. It is one set of `TEMP VIEW`s in `ratings.php`, created by `musicRatingView($db)` on each request that reads ratings (the song list, both lists, both cards, the home page, `song-rating`, the poll and `song-relationship`), rather than borrowing worked out per reader: shared SQL, the exception LFT weighs, because seven readers agreeing is the point. A borrowed average is rounded to two decimals in the view, so a cell, a statistic and a sort all see the same number, and the newest note is found with `NOT EXISTS`, not a window function, since the host's SQLite version is unknown. **Shown faded, beside an empty value**: `songRows.php` leaves the cell's own value empty and puts the borrowed one in a `.songInherited` span, so the editors only ever touch what was written, and the graph draws a borrowed dot faded. **The blind-rating gate treats it as a rating**: the reader's own borrowed rating uncovers everyone else's on the song (the owner's choice), and another rater's borrowed one is covered like a real one. **Live**: the server works borrowed values out and the page only writes them. The poll carries, with each change, the same account's ratings on the songs it lends to and their statistics; `song-rating` answers with `ratings` (this account, the written song and its versions, so a cleared score borrows again) and `relatedStats`; `song-relationship` answers with every account's `ratings` and the `stats` of the songs it touched. Each entry says which half is borrowed. Hovering a rating cell lists what that rater really wrote on each version as a sentence, "You scored the remastered version (2: Remaster Song) 8", or "Alice wrote about the original version (5: …):" with the note on the next line, read by the page off those songs' own cells, leaving out a value the gate still covers there (revealing it adds it); the version is named by its own end of the relationship (`variantNoun`/`targetNoun`), and "You" and a name are separate strings, since other languages conjugate the two differently. The sentence is bold and the rating plain (the owner's wish: what somebody wrote is not part of the heading), through `data-tooltip-rich`, the template split at `{value}` before anything is filled in, so it holds wherever a language puts the value.
- **Average/median/mode/σ are worked out in PHP, not SQL** — SQLite has no `stddev()` and median/mode are painful in SQL. `musicScoreStats()` in `app/modules/music/stats.php` is the only implementation: `ajax/albumCard.php` calls it twice over one query pivoted two ways, per account for the ratings table and per song for the track columns. Keep it that way — written out at both sites (as it was), "fixing" one to sample σ would leave two σ columns on the same card computed differently with nothing on screen to say so. It sorts its own copy, so callers need not. A per-rater row's numbers are over *the tracks that rater scored*, never over the album, which is why every row also prints `rated / total`. The `tfoot` totals row is the same five numbers over **every score on the album pooled** — not the mean of the per-rater means, which would let someone who rated one track weigh as much as someone who rated fifteen — and its `rated / possible` is the column total of the rows above it (tracks × accounts). It shares its cell rendering with the rater rows through `scoreStatCells()`, so neither — nor the artist card's per-album row, which uses it too — can drift into formatting or colouring a score differently, and why all-distinct scores print no mode at all rather than listing every score as one.
- **The total is `sum` in code, and it is empty rather than 0 when nothing is rated.** Every score added up: the number that ranks a song three people gave 7 above one somebody gave 10, which the average ranks the other way round. It is on every surface the other statistics are — the song list's columns and their poll/write updates, both lists, both cards' ratings tables, the artist card's album table, the album card's track table, and the graph's orders. It is `sum` rather than `total` everywhere below the label because "totals" already means the pooled Everyone row (`$statsTotals`, `albumStatsTotalRow`). A sum over no scores is null like every other statistic, not 0: one score of 0 sums to 0 and must not read the same as none, and the blind-rating gate covers any non-empty statistic, so a 0 would put a pill over a value nobody gave. It sorts to the bottom from either end as a result, which is the average's rule and not the `rated` count's. It is not a score, so it is never on the 0-10 ramp: `scoreStatCells()` renders it uncoloured with the deviation, and its song-list column is not `score => true`, which is what keeps `SONG_RAMP_FIELDS` from painting it on reveal. It *is* covered by the gate, since a song with one rating has that rating as its total.
- **The artists and albums lists carry the same statistics, one column each.** `/music/artists` and `/music/albums` run `musicScoreStats()` over every score on that artist's songs or that record's tracks — pooled, which is the figure the matching card's `tfoot` prints — and render it with the same `scoreStatCells()` the cards use. That function takes **which** statistics to emit: the cards ask for five (average, σ, median, mode, total), the lists for seven, adding highest and lowest. Their `rated / possible` is songs × accounts and tracks × accounts, matching each card's totals row. Each list also counts what it is a list of — songs and albums for an artist, tracks and total runtime for a record, that runtime being the sum of **the tracks that carry one**, on the same principle as a statistic being over the songs that were scored. The four `td.albumStats*` rules moved out of the `.albumCard, .artistCard` nesting to the top of the stylesheet when the lists started carrying those class names; they are shared chrome now, not card chrome. Every one of those columns sorts, which is its own note below.

### Linking and sorting

- **An open card is in the address, so it can be linked.** `public/modules/music/js/cardLink.js` (loaded by `partials/albumCardModal.php` **before** `albumCard.js`, and so before `songs.js` on the pages that load it) holds `writeCardLink()`/`cardLinkValue()`; opening a card `replaceState`s `?songCard=`/`?albumCard=`/`?artistCard=` in, closing takes it out, and each script restores its own kind on load. Four things this has to get right: the parameters are **not** the existing `artist`/`album`, which already mean "show me only this one's songs" on the same page; each modal clears only the parameters it owns, because the album card genuinely does open *over* the song card and both belong in the link; `songQuery()` in `songs.js` re-adds whatever card is open, since it rebuilds the address from scratch every time the sort or filter changes and would otherwise drop it; and `openCardModal()` refuses a **hidden** card, which a link can ask for when the filter in the same address leaves that song out — it would be moved into the modal and stay hidden, leaving an empty box. `replaceState` not `pushState`, like every other control on the page: back leaves the page rather than stepping through everything looked at while on it.
- **Sorting the song list keeps blank cells at the bottom in *both* directions**, so flipping a column reverses the rows that have a value and leaves the gaps where they are. Nothing recorded is not a low value — a song with no year is not older than every song that has one — and this is what the album card's graph has always done with its own orders. It has to be settled **before** the direction is applied, in all three places that sort: `sortRows()` in `songs.js` (which is where the page's sorting actually happens — the header links only set the first render), `songsOrderBy()` in `routes/songs.php`, and the statistics `usort` below it. SQLite will not do it unasked, since a NULL is simply the smallest thing there is; hence `$sortable` holding two expressions per column, a bare `value` to test for emptiness and an `order` that may collate. `''` counts as empty alongside NULL, because that is what the cell shows either way and the client sorts on the cell. Get any one of the three out of step and clicking a header gives a different order from reloading the link that same header writes.
- **The song list's statistics columns are sorted in PHP, and updated by the poll.** `/music/songs` carries the same eight numbers per song (average, σ, median, mode, high, low, total, count) to the right of the rater columns, deliberately past the width of the screen. Three consequences. (1) They are **not** in `$sortable` and must not be: that array goes straight into `ORDER BY`, and SQLite can compute none of them — `routes/songs.php` sorts those rows itself after the fetch, off the scores the query already pivoted into each row, so no second query. (2) The **mode** column prints every tied score and therefore cannot be compared as a number — it carries `data-sort-value` with the highest of them (what the album graph's mode order uses), which `fieldValue()` prefers over the cell's text. (3) They would go stale the moment anybody rated anything, so `ajax/songRating.php` returns `stats` for the row it just wrote and `ajax/songRatingPoll.php` returns `stats` for every song in that tick's changes. Both come from `musicSongStatFields()` in `stats.php`, which returns the finished **strings** — the client only writes what it is handed. Do not reimplement the maths in JS to save the round trip; that is precisely how one place ends up on population σ and another on sample with nothing on screen to say so. (`scoreText()` moved to `format.php` for this: an endpoint has no business requiring a view partial.)
- **The artist and album lists sort in one place, and it is PHP.** `app/modules/music/listSort.php` is all of it. Each route declares its own columns as `key => [label, class, value]`, `value` being a closure that reads that column out of a row, merges in `musicListStatColumns()` for the eight both share, and hands the lot to `musicListSorted()` and `musicListHeaders()`. Nothing reaches `ORDER BY`: the statistics are worked out in PHP after the fetch, so SQL could only ever sort half the columns, and the song list's rule that its three sorts have to agree is answered here by there being one. Blanks still settle **before** the direction is applied, but with a distinction the song list never has to draw — a **count** of nothing (no songs, no tracks, nothing rated) is a count and sorts as zero, while an unknown runtime, or an average nobody has contributed to, is empty and sinks to the bottom whichever way the column points. `text` on a column picks `strcasecmp` over `<=>`, standing in for the `COLLATE NOCASE` the query used to do. A sort key *or* direction the list does not have falls back to name, ascending, rather than being coerced. Neither page loads a line of JS, so the header links are the whole mechanism, and they carry no filter state because these lists have no filters. The header row is generated from the column list while the body row is written out by hand, a pairing that can drift silently; a test in `tests/cases/catalogue.php` counts the two against each other.

### Shared helpers and live updates

- **Two small shared helpers, both deduplicated after they drifted apart in review:** `app/modules/music/format.php` has `musicDuration()` (seconds → `M:SS`, null stays empty) and `musicSongLabel()` (`Artist — Title`, used by the audit page *and* the rating popups, which have to agree); `links.php` has `spotifyTrackIdIn()`/`youtubeVideoIdIn()`, whose two callers keep deliberately different fallbacks — `ajax/songLink.php` keeps a value with no id in it as pasted (it may already be a bare id), `views/partials/songRows.php` treats no-id as "don't embed". Only the patterns are shared, so adding a URL shape reaches both.
- **Live rating updates use one poll with two cursors that behave oppositely — do not "harmonise" them.** `/music/ajax/song-rating-poll` takes `since` *and* `sinceAudit` in one request. `since` filters `account_song.updated_at` with an **inclusive** `>=`, so it deliberately re-delivers the same row every tick (a test pins this: a second write inside the same one-second stamp must not slip through); that's harmless because the client just rewrites cells to the same values. `sinceAudit` filters `rating_audit.id` with a **strict** `>`, because those rows drive one-shot popup notifications and an inclusive cursor would re-fire the same popup every 3 seconds forever. Making either match the other breaks one of the two features, silently.
- **How long a toast stays is the account's, from the cog menu.** `account.toast_seconds` (migration `008`, default 180) holds one of `MUSIC_TOAST_CHOICES` in `toastDuration.php`: seconds, with `0` meaning rating toasts are off and `-1` meaning they stay until closed. It travels like `blind_rating`: loaded into the session at login, dropped at logout, read through `musicToastSeconds()`, handed to `songs.js` as `#songToastSeconds`. The settings route reads "missing" the other way from the checkbox beside it: the select always sends a value, so a missing or unknown one leaves the stored choice alone rather than resetting it. **Off silences only the rating toasts.** `showRatingEvent()` returns early, but the "not saved yet" warning from the outbox below still shows, at `TOAST_DEFAULT_DURATION`, because apart from the cell's styling it is the only sign that a typed rating never arrived, and the Result column is off-screen. Until-closed sets no timer at all, so `TOAST_LIMIT` is what stops those toasts piling up.
- **A rating that cannot reach the server is kept and resent, not reverted.** `songs.js` holds an outbox of score and note writes in `localStorage` under `musicUnsavedRatings:<account id>` (the id comes from `#songAccountId`), one entry per song and field. Every save is queued **before** it is sent and taken out once the server answers, so a write that dies on the way — offline, a hung connection (saves give up after 10 s), the tab closed mid-save — is still there. `sendRating()` sorts the outcome four ways, and the split is the whole point: an answer of `status: "error"` or any other 4xx is a **refusal** and is dropped and reverted as before, since resending a bad score or a deleted song can never succeed; no answer, a timeout or a 5xx is **offline** and is kept, the typed value stays on screen with `songCellUnsaved` (both copies of the cell) and a toast, because the Result column is off-screen to the right; 401/403 is **logged out** (or a CSRF token a re-login replaced), which stops automatic resends until a fresh page load, where the outbox is replayed with the new token. Resends run one at a time from `flushUnsavedRatings()` — on load, on every answered poll, on the `online` event and on a backing-off timer (3 s up to 60 s) — and stop at the first that gets no answer. Four things it relies on. The key carries the account id, so a different account in the same browser never sends someone else's ratings as its own. The outbox is read fresh from storage every time, so two open tabs share one rather than each resending a stale copy, and an entry is only removed while it still holds the value that was sent. `pending` goes on **both** copies of the cell (it used to go on the edited one only, which let a poll tick overwrite the other mid-save), and `applyRatingHalf()` skips pending cells, which is what stops the poll writing the server's old value over a queued one. And resending is safe to repeat because an identical rewrite is a no-op for `rating_audit`. **The latest send wins**, by the owner's choice: a score queued offline and resent later overwrites whatever that account wrote in the meantime from another device; there is no compare-and-set. When storage is refused (a private window, blocked site data) the outbox lives in the page instead, and only then does leaving the page warn. Admin edits (title, artist, album, year, links) still fail and revert — `saveCell()` hands only `song-rating` writes to the outbox.
- **`rating_audit`** (migration `005`) is an append-only log of score/note writes — one row per change with `value`, `previous_value` and the account, written by `ajax/songRating.php` inside a transaction with the `account_song` upsert. The transaction matters: a state change without its audit row is invisible forever, since the audit cursor only ever moves forward. Identical rewrites are deliberately not logged. `account_song` still holds only current state; this table is the only history.
- **`edit_audit`** (migration `009`) is the same log for what admins change, and `/music/audit` lists both, newest first, as one History. Every admin write logs through `musicLogEdit()` in `editAudit.php`, inside the transaction that holds the write, and a write that changes nothing logs nothing, since the card editors save on every blur. Each row names a song, album or artist (`kind`, `entity_id`) and a field, with the value before and after **as text at the time**: names, not ids, so a later rename cannot change what an old row says, while the page shows what the row is about under its current name, as it always has for ratings. It is a table of its own because `rating_audit` has two readers that must never see an edit: the poll, whose strict audit cursor turns every row into a toast, and the borrowed-note views in `ratings.php`, which read its note times. Three shapes are worth knowing. **A song on an album is logged on the album**, as a `track` line the way the album lists it (`3. Title`, under the name it is listed by), whichever card or the import made the change, so adding, renumbering, relisting and removing a track all read as one line changing; `musicWriteTrack()` does the write and the log together. **A relationship is logged on its variant** (`relation`, JSON of the type and the target song's id and title, rendered as the variant's card reads it, in the reader's language by `musicAuditValueText()`), and a row whose variant changes is a removal from one song and an addition to the other. And **a name made current is a `name` (or `title`) change**, the name it replaced staying as another name, while a name added beside it is an `alias`. The import's Extras step goes through the card's own endpoints, so its links, years and durations log like any card edit. The page pages through both tables at once with a cursor of `created_at`, the log and the id (`?before=1793000000-edit-12`), since the two ids are separate sequences; within one second a rating sorts above an edit.

### Layout traps

- **Sticky table header: its borders are `box-shadow`, not `border`.** Under `border-collapse: collapse` the *table* paints collapsed borders, so they stay behind at the table's original position when `thead` sticks — real borders on header cells look correct at rest and vanish the moment the header locks (rows then show through the 1px seams). Every header edge is therefore an `inset` shadow, drawn right-edge-per-cell so shared separators stay 1px. The song table itself has been `border-collapse: separate` since 2026-11-03, for a different reason: a collapsed line is centred on the column's edge and rounds per column, so the rater edges (coloured then, since removed) sat up to a pixel apart between header and body, by an amount that changed per column and per display scale (4 of 10 edges off at 100% in Chrome). It stayed when those edges went: the reader's own accent edges need the same, and the column picker's left-edge chain is written for it. Separate gives a body cell the same box as the header cell above it. Each `td` draws its own right and bottom side and the first column its left, or the lines would double up. Related trap: `.songListScroll` must **not** regain `overflow-x`, because one axis of `auto` makes `overflow-y` compute to `auto` too, turning it into a scroll container — the header would then stick to *that* box (which never scrolls vertically) instead of the viewport. The cost of removing it is that an over-wide table scrolls the page sideways.
- **`--navHeight` is measured in JS**, published onto `<html>` by a `ResizeObserver` in `public/modules/music/js/nav.js` — loaded by `nav.php`, so it runs on every music page, not just the song list — and consumed by CSS for the body's top padding, the sticky header's top and the toast stack. The nav wraps, so hardcoding it reopens the bug where body rows show through the gap between the nav and the locked header. Measure with `getBoundingClientRect().height`, not `offsetHeight` — the latter rounds to whole pixels, which is what made a 1px fudge necessary before. It is set once synchronously as well as on every observer tick, because the body's top padding now depends on it and the `3.35em` fallback in each `var()` is only a one-line nav's worth. (It was `--songNavHeight` in `songs.js` while the sticky table header was its only reader; there was a `--songHeaderHeight` beside it, read only by the note preview panel's sticky offset, which went when that panel was deleted.)
- **The nav is `position: fixed`, and the page is as wide as its widest table.** Those two go together and both exist because an over-wide song table scrolls the *page* sideways (see the `overflow-x` trap above), not a box inside it. A sticky nav slides away on that axis — sticky needs slack between the element and its containing block, and a full-width bar has none — so the bar is fixed at `left: 0; right: 0` and `body` carries `padding-top: var(--navHeight, …)` in its place. The gradient then has to reach the far end of that sideways scroll, which it does by `body { width: min-content; min-width: 100% }`: min-content is the song table, which cannot shrink, while prose keeps wrapping because min-content sizing of text is one word. Two things make that work and each is easy to undo by accident. `:root` carries `background-color: #000000` — without a background on the root, the body's gradient is propagated to the canvas and painted against the *root's* viewport-wide box, tiling at the viewport edge no matter how wide the body is. And `.songLayout`'s second column is `minmax(min-content, auto)`, not `minmax(0, 1fr)`: a grid item spanning a flexible track is skipped while the container's min-content size is worked out, and the song list spans both columns, so a `0` minimum or an `fr` maximum leaves the table contributing nothing to the body's width — it stays viewport-wide and the gradient stops dead at the fold. Both halves matter and only one is visible in Chrome, which credits the table against a `minmax(min-content, 1fr)` track anyway; Firefox applies the skip as written and does not. Check a change to that line in both.

### The home page

- **`/music` is a list of links the owner picked, each a view of the song list**, and it is where login and register land (owner, 2026-11-05); signed out, it sends you to login. A link is a `home_link` row (migration `009`) holding the view as parts, a filter and a sort, never as an address: one of `artist_id` or `album_id`, or neither for every song, and a `sort` and `dir` from the song list's own keys. `homeLinks.php` turns the parts into the address, in `songQuery()`'s parameter order, and into the text. **An album link's artist is read off the album when the page is drawn**, not stored, because the song list only takes an album beside its own artist (its in-scope rule), and an album's artist can be changed on its card. A link with no label reads as the heading the song list will show for it, followed by the order when it is not the default ID ascending ("Some Artist · Alice score ▼"), so a rename reaches the link too. A link may carry a one-line note. Above the list is a welcome line, shown only when there are links, since it promises some below.
- **Under each link, how much of it is rated**: "You rated X of Y songs (Z%). Everyone together gave W of V possible ratings (U%)." Y is the songs the link's filter shows, worked out as the song list filters (an album's tracks, else every song any of whose artists is the artist, else every song, and a filter naming nothing that exists counts as none), and V is Y × accounts, the `rated / possible` the cards and lists already print. A rating is a score, never a note, and it is read from `effective_rating`, so a borrowed score counts here as it does everywhere else; nothing is covered by the blind-rating gate, which never covers a count. `musicHomePercent()` rounds, but only says 0% or 100% when it is exactly that. The queries run once per page, not per link: `musicHomeSongRatings()` gathers every song's artists, albums and scores, and each link is one pass over that.
- **The picker is on the page itself, for admins, and needs no JS**: a folded Edit links box under the list, one form per link (label, note, Filter, Sort by, Direction, then Save, ↑, ↓, Delete) and one to add a link, all posting to `/music` and redirecting to `/music?edit=1`, which renders the box open. Filter is one select (All Songs, then every artist, then every album headed as the song list heads it), so no album can be picked beside the wrong artist. A filter, sort or direction the song list does not have writes nothing and says nothing, since only a tampered form sends one. ↑ and ↓ renumber every row, so links that somehow share a position still swap. **These writes are not in `edit_audit`**: that log is about songs, albums and artists, and History names each row by the thing it is about.

### What's New

- **Music's changelog is a page, `/music/changes`, not `CHANGELOG.md`** (owner, 2026-10-27), because that is where its users are; the other modules still use `CHANGELOG.md`. Entries live in `app/modules/music/changelog.php`, releases newest first, **each release one list with no kinds of change** (the owner found Added, Changed and the rest pointless, 2026-11-05), each entry keyed by locale: `en` is required, and `fy` and `de` are drafted beside it in the same change (`tests/i18n-coverage.php` lists any missing). A missing or blank locale falls back to English, as the catalogue does. What deserves an entry follows the global changelog rules. **An entry is one short line saying what changed**, never how to use it (owner, 2026-11-05: "Noone will read a book"); several small changes to one feature make one line. The global layout does not apply either: an entry users must act on goes first in its release and opens in bold, with no heading of its own. Text is escaped, and `**…**` is the only markup. **What only admins can use is marked `'admin' => true`** (card edit mode, Add Songs) and listed after everyone's changes in its release, under a plain For admins heading (owner, 2026-11-05). Everyone sees it, by the owner's choice; `musicChangeEntries($release, $forAdmins)` in `changes.php` builds either list. An entry that is partly for everyone is split in two, as the Related row's was. **The undated release is headed "Latest changes", never "Unreleased"**: the owner deploys before a date is written in, so the live site shows that section as it stood at the deploy until the next one, and to a reader it is simply the newest changes. On a deploy it takes the date and an empty undated release goes on top; a release with nothing in it renders nothing.

### Auth, i18n and bulk import

- **Auth/session:** `app/session.php` provides `sessionScope()`-namespaced sessions (hideandseek is the second consumer, with accounts entirely separate from music's), CSRF via `csrfToken()`/`checkCsrf()`, and `requireLogin()`/`requireLoginJson()` guards. `app/modules/music/auth.php` layers admin-only checks on top.
- **i18n:** `loadStringCatalogue($module)` selects a module's strings; `stringCatalogue()` reads them back and `t($key, $params)` translates. Each module has `lang/en.php` (the source catalogue, always complete) plus `lang/<locale>.php` overlays (every locale file, English included, is only an `array_merge` of its `lang/<locale>/*.php` part files — `common`, `accounts`, `artists`, `songs`, `albums`, `audit` — so a new key goes in a part file); missing/blank overlay keys fall back to English automatically. Active locale comes from that module's own session entry (see **Browser preferences are per module** below), else the `LOTSOFS_LOCALE` env var, else the module's own `defaultLocale` in `app/modules/<name>/config.php` — `fy` (West Frisian) for music, `en` for hideandseek. The test harness sets `LOTSOFS_LOCALE=en` so assertions can match English text. `tests/cases/strings.php` fails the suite if a catalogue key is referenced nowhere (`t('literal.key')` must appear verbatim somewhere under `app/modules/music` or `public/modules/music` — dynamic/glued key lookups don't count) or if a key exists in one locale but not another. **Both that test and `i18n-coverage.php` are hardcoded to the music module**, so hideandseek's catalogue has no orphan or coverage check at all — widen them rather than assuming a green suite says anything about it.
- **Bulk import** (`/music/add-songs`): paste tab-separated rows, then a column-mapping step lets you assign each column a role (Artist/Title/Album/Track#/Year/Duration (`M:SS` or seconds, written via `/music/ajax/song-duration`)/one of the link platforms/Ignore) rather than assuming a fixed column order — content is auto-guessed where it's unambiguous (a Spotify/YouTube/SoundCloud/Bandcamp URL or a bare Spotify/YouTube ID), position-based only for the first four columns. Wizard order is Artist → Song (titles/aliases only) → Extras (links + year, confirm-and-submit, generalized for future per-song data) → Album (its year input pre-filled from whatever the Extras step just confirmed) — Extras deliberately runs *before* Album so the year is available to pre-fill it. **A title the artist already has is matched to that song**, and the Extras step then writes the row's links, year and duration onto it. That is right for a song pasted twice and wrong for another recording of it, so a row whose title matched also offers `<New, separate>`: `song_id: 'separate'` creates the song without `song.php`'s same-artist-same-name check, which still answers `duplicate` for a plain `new`. It is offered only there and never chosen for you, but one checkbox above the Song table sets every such row to it at once, or back to its match (the owner found 19 dropdowns tedious); it ticks itself from the rows, half-filled when only some are separate, so a row changed by hand afterwards is still shown truthfully. A select under that box then says once how every separate song relates to the one it shares a title with, and `song.php` writes that `song_relationship` row in the same transaction. Rename and adding a name (`songEdit.php`, `aliasAdd.php`) still refuse a name another song by the artist has, so the import is the only way two songs by one artist come to share one. **The Song step settles such twins by album, or not at all**: a title more than one of the artist's songs has preselects the one on the pasted row's album, by any of that album's names, when exactly one is, and otherwise starts on `<Choose a song>` and holds Submit until it is chosen. The albums come with the artist step's answer (`song_albums`), and every option reads `139: Title · Album`; the album card's song list, which carries no albums, adds an id to a label that repeats.
